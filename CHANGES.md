# Что сделано — пояснения к проекту

## Этапы разработки (Git-история)

Проект развился в три этапа, отражённых в коммитах и тегах:

- **PR1** (`pr1`): начальный сценарий — простой `main.py` с базовыми
  конструкциями Python (типы, ветвления, функции, импорт `datetime`).
- **PR2** (`pr2`): модульная структура — `documents.py`, `users.py`,
  `approvals.py`, `storage.py`, `utils.py`, JSON-хранилище, обработка
  исключений, первые тесты pytest.
- **PR3** (`pr3`): переход к ООП — пакет `models/` с классами
  `Document`, `User`, `Approval`, декораторы `@classmethod` и
  `@staticmethod`, обновлённые тесты.

## Финальная версия (после упрощения)

После обсуждения с пользователем проект упрощён до чистого CRUD: для
каждой сущности доступны операции **создать / найти / обновить /
удалить + вывод списка**, плюс работа с JSON.

### Что было убрано как over-engineering

- `Document.is_overdue()` — проверка срока (логика выведена из класса);
- `Document.get_status()` и `Document.get_status_label()` — вычисление
  статуса документа;
- `Document.validate_title()` (`@staticmethod`) — валидация названия;
- `filter_documents_by_type()` — фильтрация по типу;
- `sort_documents_by_deadline()` — сортировка по сроку;
- `find_document_in_list()` и `find_user_in_list()` — дубликаты поиска
  (используются `find_document` и `find_user` из соответствующих
  модулей);
- `is_document_open_for_approval()` — внутренняя проверка, перенесена
  в тело `add_approval()`;
- `can_approve_document()` — отдельная функция проверки, логика
  включена в `add_approval()`;
- `cancel_approval()` как отдельная функция — отменённое согласование
  теперь обновляется через `update_approval(is_cancelled=True)`;
- `get_approval_status()` — вычисление статуса.

### Что осталось

Для каждой из трёх сущностей (`Document`, `User`, `Approval`):

**Класс** (атрибуты + 4 метода):
- `__init__` — конструктор;
- `__str__` — строковое представление;
- `from_data` (`@classmethod`) — создание из словаря JSON;
- `to_dict` — преобразование в словарь для JSON.

**CRUD-функции** (4 + 1):
- `add_*` — создание;
- `find_*` — поиск по идентификатору;
- `update_*` — обновление (только переданных полей);
- `delete_*` — удаление;
- `show_*` — вывод списка.

**Бизнес-правила в `add_approval`:**
- автор документа не может согласовать собственный документ;
- на один документ — не более одного активного согласования.

### Принципы ООП в проекте

- **Инкапсуляция:** данные сущности и операции, относящиеся к ней,
  объединены в одном классе.
- **Полиморфизм:** метод `__str__()` реализован в каждом классе и
  возвращает подходящее представление. `print(document)`,
  `print(user)`, `print(approval)` работают единообразно.
- **Композиция:** согласование `Approval` хранит идентификаторы
  связанных документа и пользователя. В JSON — `document_id` и
  `user_id`. При загрузке связи восстанавливаются через `find_document`
  и `find_user`.

### Декораторы

| Декоратор | Где применяется | Зачем |
|---|---|---|
| `@classmethod` | `from_data()` всех трёх классов | Создание объекта через класс `cls` из словаря данных JSON. |

### Хранение объектов в JSON

- JSON-файлы не содержат внутренней структуры Python-объектов — только
  данные, позволяющие восстановить объекты.
- `Document` и `User` сохраняют все свои атрибуты напрямую.
- `Approval` вместо ссылок на объекты хранит идентификаторы
  (`document_id`, `user_id`).

При загрузке:
1. Загружаются документы → `List[Document]`.
2. Загружаются пользователи → `List[User]`.
3. Для каждого согласования из `approvals.json`:
   - по `document_id` находится объект `Document`;
   - по `user_id` находится объект `User`;
   - создаётся объект `Approval` с восстановленными связями.

## Запуск и проверка

```bash
# Установка зависимостей
pip install -r requirements.txt

# Запуск программы
python main.py

# Запуск тестов (должно быть 30 passed)
pytest -v

# Проверка качества кода (без замечаний)
flake8 .
```
